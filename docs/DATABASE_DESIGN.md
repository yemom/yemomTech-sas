# Database Design

PostgreSQL 17. **Flyway owns the schema**; Hibernate runs with
`ddl-auto: validate` and only checks that entities match. All migrations live
in `backend/src/main/resources/db/migration/` (V1–V7). Timestamps are
`TIMESTAMP WITH TIME ZONE` stored in UTC (JDBC `time_zone: UTC`).

## Conventions

- **UUID primary keys** — generated by the application, no sequences to leak
  row counts.
- **Soft state transitions** — `status`/`revoked_at`/`accepted_at` columns
  instead of row deletion wherever history matters (orgs, websites,
  memberships, invitations, refresh tokens).
- **CHECK constraints mirror enum values** — the DB rejects invalid states
  even if application code regresses.
- **Every tenant-owned table carries `organization_id`** with
  `ON DELETE CASCADE` from `organizations` (see MULTI_TENANCY.md).
- **Secrets are hashed** — only SHA-256 digests of refresh/invitation tokens
  are stored; passwords are BCrypt (60 chars).

## Entity-relationship overview

```
users ──< organization_members >── organizations ──< websites
  │                                     │
  │                                     ├──< organization_invitations
  │                                     └──< audit_logs (SET NULL)
  └──< refresh_tokens (family_id groups one login session)
```

## Tables (migrations)

### V1 — `users`
Every account. Email is normalized (trimmed + lowercased) by the app; the
`UNIQUE (email)` constraint is the last line of defense against racing
registrations. `password_hash` is BCrypt. Statuses: `ACTIVE`,
`PENDING_VERIFICATION`, `SUSPENDED`, `DEACTIVATED`.

Checks: non-blank first/last name, email contains `@`.

### V2 — `refresh_tokens`
Opaque 256-bit random tokens; **only the SHA-256 hex digest is stored**
(`length = 64`, unique) so a DB dump cannot be replayed.

- `family_id` — groups every token issued in one login session; reuse of a
  rotated token revokes the whole family (anti-replay).
- `replaced_by` — the successor of a rotated token (audit chain).
- `revoked_at` partial index (`WHERE revoked_at IS NULL`) — the hot
  "active token for this cookie" lookup.
- **No IP addresses are stored** (privacy): `device_information` is a coarse
  label like "Chrome on Windows".

### V3 — `organizations`
The tenant. Column-level Ethiopian defaults — a row can never exist without
them, yet nothing in business logic hardcodes them:

| Column | Default |
| --- | --- |
| `country_code` | `ET` (`^[A-Z]{2}$`) |
| `currency_code` | `ETB` (`^[A-Z]{3}$`) |
| `timezone` | `Africa/Addis_Ababa` |

- `slug` — URL-safe identity, unique, generated by `SlugGenerator`
  (`^[a-z0-9]+(-[a-z0-9]+)*$`), **immutable after creation** (renaming the
  org does not change links).
- `status` — `ACTIVE` / `SUSPENDED` / `ARCHIVED`. Deletion is **soft**:
  the API never removes rows, preserving auditability and recovery.

### V4 — `organization_members`
**Membership is the only proof of tenant access** — the JWT never proves
organization authorization (MULTI_TENANCY.md).

- `UNIQUE (organization_id, user_id)` — a user holds at most one role per
  org; a user may belong to many orgs.
- Roles: `BUSINESS_OWNER`, `BUSINESS_ADMIN`, `MARKETING_MANAGER`,
  `SALES_MANAGER`, `SALES_AGENT`, `ANALYST`, `VIEWER`.
- Statuses: `ACTIVE`, `SUSPENDED`, `REMOVED` (suspended/removed members keep
  the row but lose all access).
- Index `(organization_id, membership_status)` for listing pages.

### V5 — `organization_invitations`
- `invitation_token_hash` — SHA-256 digest, unique; the raw token exists
  only in the outbound e-mail link (dev mode returns it in the API response
  behind `expose-dev-token`, which startup validation forbids in production).
- `expires_at` — **7 days** from creation.
- `ck_invitation_state`: a row is accepted *or* revoked, never both →
  single-use by construction.
- Partial index for pending invitations per org.
- The invitation is **bound to `invited_email`**; accepting accounts for a
  different address is rejected (403).

### V6 — `websites` (first vertical slice)
- `domain` — application-normalized (lowercase host, no scheme/path/dot),
  `UNIQUE (organization_id, domain)`: two tenants may register the same
  domain, one tenant may not duplicate it.
- `url` — the full normalized URL (`^https?://` check).
- `status` — `ACTIVE` / `INACTIVE`; deactivation is **soft**, the row stays.
- **No fetching**: registration is metadata-only by design — there is no
  crawler in this slice, hence no SSRF surface.

### V7 — `audit_logs`
Append-only trail of security- and organization-level actions.

- `action` matches `^[A-Z][A-Z0-9_]*$` (e.g. `WEBSITE_REGISTERED`).
- `metadata` JSONB only for flexible context; the application **drops any
  key that looks secret** (password/token/secret/…) before insert — the
  table never stores passwords or raw tokens.
- `ON DELETE SET NULL` for org/actor: the trail survives user/org purges.
- Indexes: `(organization_id, created_at DESC)`,
  `(actor_user_id, created_at DESC)`, `(target_type, target_id)`.

## Migration discipline

- One concern per version, forward-only; never edit an applied migration —
  add a new `Vn__…sql`.
- `validate-migration-naming: true` enforces the `Vn__description.sql` format.
- CI runs `./mvnw -B verify`, which applies all migrations to a fresh
  Testcontainers database and then validates entities against them.

## What is intentionally absent

- No `payments`, `invoices`, `ai_runs`, or `metrics` tables — those product
  areas do not exist yet and nothing is faked.
- No org-restore/undelete flow yet (archive is one-way until ROADMAP item
  lands); no table prevents adding one later (`status` can return to
  `ACTIVE`).
